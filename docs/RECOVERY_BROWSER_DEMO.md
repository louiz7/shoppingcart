# Browser demo

`/demo` is a public, no-login voice demo. It runs the production `RecoveryAgent` and GPT-Live model over LiveKit browser audio, with the same profile, conversation instructions, function schemas, product search/details, policy reads, product selection and discount validation.

The fixed source is the internal test shop `test-store-slzn5m7l.myshopify.com`. Each start loads its most recently updated unfinished cart among the ten latest created abandoned checkouts, current product prices, public knowledge and approved offers (30-second source cache). No customer name, email, phone, address, checkout token or personal recovery URL is queried. If source lines are unavailable, the demo fails visibly rather than substituting a fictional cart.

The demo tools have their own session records, room prefix and token namespace. They never call the telephony, SMS, contact, order or conversion mutation paths. Sending a link means displaying a fresh cart permalink in the same browser session; it contains only selected variant IDs, quantities and an explicitly accepted, backend-verified discount. The original abandoned checkout is untouched. Contact stops affect only the demo session; order status never reports a real purchase. The page and agent explain these boundaries.

Sessions last at most five minutes. A database lock enforces two concurrent sessions, three starts per client per hour and twenty starts globally per hour. Starts that fail downstream still count. IPs are keyed hashes; browser capabilities use HTTP-only, Secure, SameSite=Strict cookies; worker capabilities are separate. Only transcript event identity/order is persisted, not text or audio. Expired records are removed after one day on the next start. The model receives live audio for the conversation. Room permissions allow microphone publication only, no client data or metadata writes.

Activation requires `RECOVERY_BROWSER_DEMO_ENABLED=1` in the isolated API/agent environment and the existing named agent service running. `RECOVERY_LIVE_ENABLED`, `RECOVERY_SMS_ENABLED` and `RECOVERY_WORKER_ENABLED` can all stay zero. The worker rejects phone jobs in this mode. Nginx grants microphone=(self) only on `/demo`; all other routes keep their existing policy. Deploy application changes through the Ecom GitHub Actions workflow; provision the flag and route-specific microphone policy as runtime configuration.

Verification: Node integration tests cover session/worker-token separation, conversation readiness, reviewed versus merely prepared offers, interrupted reviews, no-discount links, alternative selections, stopping, public link construction, microphone-only tokens and concurrency limits. Offline SDK tests cover browser participant selection, tool routing, cleanup and phone-job rejection. Test a real browser session before reporting audio verified.

References: [LiveKit job lifecycle](https://docs.livekit.io/agents/server/job/), [JavaScript SDK](https://docs.livekit.io/reference/client-sdk-js/), [agent state events](https://docs.livekit.io/reference/agents/events/). CLI/docs MCP were unavailable; API signatures were checked against the installed Python/Node SDKs and official web documentation.

The founder persona may play the founder in the browser demo greeting; the page labels this as AI roleplay. Direct identity questions are answered truthfully. This demo-only greeting and identity instruction never apply to phone calls.

For checkout testing, set `SHOPIFY_STOREFRONT_PASSWORD` in the dashboard's private runtime environment. The demo then shows two steps: unlock the test shop in a new tab, return to the demo and open the original prepared checkout link. Shopify's development-store password endpoint redirects to the shop home page, ignoring checkout return parameters. `/demo/unlock` accepts same-origin POSTs only, is gated by the demo flag, and auto-submits the visitor password to the fixed test-shop password endpoint. This intentionally makes that test-shop visitor password available to public demo users; never configure an admin password or a merchant-store password here. It is HTML-escaped, sent in a POST body, omitted from normal demo data and URLs, and served without caching under a restrictive CSP. The checkout URL and its accepted-discount logic remain unchanged. Public live shops do not need this extra unlock step.

The initiating form uses `rel="noopener"`, not `noreferrer`: Chrome sends `Origin: null` with the latter, which correctly fails our origin check. The demo page sets a `same-origin` referrer meta policy so same-origin form submissions retain their Origin behind the proxy's default `no-referrer` header; external destinations still receive no referrer. The bridge response itself sets `Referrer-Policy: no-referrer` for the subsequent Shopify submission. Verification covers the built route's feature/origin gates, escaping and CSP in CI, plus a fresh local Chrome profile opening the actual UI form in a new tab and then reaching Shopify checkout in a separate tab without typing the password. No payment was submitted; Safari/mobile behavior remains to be checked.

Link consent uses the latest user event and the assistant review immediately preceding that response. A subsequent spoken acknowledgement does not invalidate the response; changed proposals and interrupted reviews still require a valid new response. Tool failures log only the operation, sanitized error code, status and demo flag, never arguments, tokens or transcript text.
